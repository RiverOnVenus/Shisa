# Window management

## Hiding and restoring windows

The session agent and its KWin script manage windows that are already open. The script matches protected apps by `desktopFileName` first and `resourceClass` second. It minimizes locked windows, sets their opacity to zero, and removes them from the taskbar, switcher, and pager. Restoration affects windows Shisa hid and preserves ordinary user minimization. When the last app is unprotected, the agent restores its windows before unloading the script.

The agent builds versioned window state from `ListApps` and `WindowStates`. The script reads it over the session bus every 250 milliseconds and applies visibility and activation changes in place. Initial startup or loss of contact can trigger a fresh `loadScript` and `run`. The agent uses separate session-bus connections for KWin calls and acknowledgements, assigns a unique plugin name, and waits for the new script's acknowledgement before unloading the old one. The agent accepts `WindowsChecked`, `HiddenWindows`, `WindowEvent`, and `RestoreIfTicketed` only from the current owner of `org.kde.KWin`. It ignores a `WindowsChecked` generation above the one it last published. `WindowState` and `HiddenApps` are read-only. `RestoreWindow` and `VerifyLock` come from the restore panel or the CLI, and restoration still passes the daemon's ticket or polkit check.

Window allowance is separate from a launch ticket. Ticket expiry affects the next launch. Manual `Lock` and the configured screen-lock policy revoke both states. A successful authenticated launch, `shisa unlock`, an allowed autostart, or a launch covered by a valid ticket sets window allowance. A daemon restart clears it, and an agent restart reads it back from the daemon.

The script reports focus changes. The agent times focus loss using `RelockSeconds`, cancels the timer on refocus or lock, and checks focus again before calling `Hide`. `Hide` drops the window permission but keeps the app's launch ticket, so a focus-loss hide does not end the grace period. Restoring the window calls `Unhide`, which needs no authentication while the ticket is still valid and asks for one after it expires or after a manual lock, or a screen lock with `clear_on_screen_lock` enabled, has dropped it. An activation of the hidden window, such as a click on the app's own tray icon, is concealed first. The script then calls `RestoreIfTicketed`, which brings the window back only when a ticket is valid and never starts polkit. Without a ticket the window stays hidden and the restore panel remains the way to authenticate. A zero grace period leaves no reusable ticket, so only the one-use ticket from an explicit unlock can skip a restore prompt, and restores ask again after it expires. `StateChanged` triggers synchronization. The setting defaults to off. A value of 0 disables it and 1 means immediate hiding. Screen-lock handling is controlled by `clear_on_screen_lock` and applies when all active graphical sessions for that user are locked.

The window layer runs as the user. Processes under the same account can interfere with the script or window properties. The tray omits a quit action that could reveal locked windows, and idle apps remain running to preserve unsaved work.

## Lock all and its result

The tray and bare `shisa lock` share the system-bus `Lock("")` contract. Success from the daemon means it revoked launch tickets and window allowance. The tray requests a fresh window check, including on repeated lock operations. The CLI requests the same check when a session bus is available. A script load acknowledgement establishes that a script ran. The window acknowledgement reports how many windows matched and how many were actually hidden. A missing or incomplete result is reported as unconfirmed.

Left-clicking the tray opens the restore panel. Right-clicking offers Lock all and settings. The tray displays the last lock result in its tooltip, and the CLI can ask the agent to verify the same operation. Restoring without a prompt uses the app's ticket; otherwise polkit authenticates first. Either way the resident script restores the original window and attempts to activate it. Before opening settings, the agent fills missing display variables from the systemd user manager's `Environment`.

The script runs inside KWin, so its behavior is tested against a fake workspace in [gate_script.test.mjs](../../crates/shisa-agent/tests/gate_script.test.mjs). That covers matching by `desktopFileName` and `resourceClass`, concealment across the taskbar, switcher and pager, restoring a window an earlier generation hid, leaving a user-minimized window alone, focus reporting and state refreshes. Real KWin behavior still needs the live checks below.

See [Tests and verification](../testing.md#window-and-authentication-verification) for coverage of real windows, missing acknowledgements, and focus-loss relocking.

On 2026-11-21, 64Gram passed live Plasma Wayland verification on KWin 6.8.3 with Shisa 0.1.0-14. Lock all hid it from the desktop, taskbar, switcher, and Overview while an ordinary window remained usable. Cancelling authentication kept it hidden. Successful authentication returned it to the foreground with its conversation and draft intact. Repeating the operation gave the same result.

KWin reported the same `internalId` before locking, while hidden, and after restoration. Multiple lock operations received window acknowledgements, and KWin still reported the pre-existing plugin loaded, supporting reuse of the resident script during the test.

On 2026-11-22, `cargo test --workspace` and `cargo clippy --workspace --all-targets` covered the `Hide`/`Unhide` split, the retained ticket, the policy decision that a ticket-covered launch restores window allowance, and the `StateChanged` value that `Hide` sends. No automated test covers the daemon's `StateChanged` after that launch. `node --test crates/shisa-agent/tests/*.test.mjs` covered the app-tray activation path: the window stays hidden and the script asks `RestoreIfTicketed` instead of showing it. `(cd gui/shisa-settings && npm test)` and `npm run build` passed, and the shell's `cargo test` (3 passed) and `cargo build --features custom-protocol` compiled the restore panel change. No automated test covers the panel's prompt or no-prompt branch or the agent's `RestoreIfTicketed` against a live daemon. On 2026-11-22, the user verified the app-tray restore path in the live Wayland session: inside the grace period the hidden window returned without a prompt, and it stayed hidden after the ticket was gone.

On 2026-11-22, a session-bus monitor showed the KWin script's `WindowState` calls arriving from `:1.11`, the current owner of `org.kde.KWin` (PID 829, `kwin_wayland`). The agent now accepts the script's reports only from that owner and ignores a `WindowsChecked` generation above the one it last published. `cargo test --workspace` (168 tests) covers the generation cap. The new agent's sender check still needs a live check with a real KWin script.
